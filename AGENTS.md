# Agent operating instructions

These instructions govern how AI agents investigate, decide, implement,
document, commit, and verify work in this repository.

## Authority and decisions

When sources disagree, use this order:

1. explicit user decision for the current task;
2. this file;
3. ADRs in 'docs/decisions/';
4. normative domain specifications in 'docs/domains/<owner>/spec.md';
5. implementation references in 'docs/domains/<owner>/refs.md';
6. current code, manifests, and generated contracts.

Do not create competing solutions or parallel sources of truth. Changes to
RN/RF, capabilities, ownership, states, authorization, security, or public
contracts require a proposal and explicit decision.

English is the canonical language for repository documentation, ADRs,
contribution rules, and official static editorial content. Product locales are
'en', 'pt', and 'es'. Do not change user-authored meaning while translating.

## Repository orientation

Before investigating code or editing files:

1. confirm the repository root, current branch, and Git status;
2. read the root 'README.md' completely;
3. read 'docs/README.md' and locate the relevant documentation;
4. read the README for the affected app, package, worker, or submodule when
   one exists;
5. inspect only the code surface material to the task.

The README explains the project and its workflows but does not override
normative rules, ADRs, or domain specifications. Do not consult legacy
references automatically; do so only when explicitly authorized and relevant.

## Architecture and invariants

- 'apps/api' is a NestJS modular monolith; cross-module contracts are exposed
  through 'public'.
- API dependencies flow from entry points and orchestration toward domain
  policy, ports/contracts, adapters, and external systems.
- 'apps/web' uses Astro pages as route-composition entry points and SolidJS
  islands; features do not import one another's internals.
- Web cross-feature composition belongs in 'src/pages'.
- Web 'store' contains application-context state; page-only state stays local.
- Every Web form, including search, has a Zod schema.
- 'packages/api-contract/openapi.json' is generated by the API and never edited
  manually.
- Worker entry points remain in runtime locations. Seeds, reset scripts,
  watchers, Docker Compose, and development orchestration stay outside 'src'.
- Layout components are structural and are not changed during migrations unless
  explicitly included in the task.
- 'content' is a Git submodule. The app records an exact content commit; after
  updating that commit, the parent repository must record the submodule change.

## Development process

Frame every task using: target, determining relations, constraints, evidence,
and uncertainty. Keep facts, assumptions, hypotheses, inferences, and
conclusions distinct.

Before a non-trivial change, inspect the applicable documentation and skill,
then present scope, invariants, risks, and verification. If new evidence
changes the scope, architecture, risk, or skill, stop and revise the proposal.

After approval, modify the authoritative owner with the smallest sufficient
intervention. Preserve behavior unless a change is explicitly authorized.
Re-check imports, contracts, behavior, generated files, and documentation.

## Pattern capture and knowledge governance

When a reusable pattern or decision emerges during discussion or implementation:

1. check whether it is already documented;
2. classify it by scope;
3. update the existing canonical source when possible;
4. update an existing skill when the pattern is a recurring technical method;
5. create a skill only when no specific skill exists and the pattern will recur;
6. document the change in the same work branch and Pull Request.

Use 'AGENTS.md' for general repository decisions, ADRs for significant
architectural decisions, domain 'spec.md' for RN/RF, domain 'refs.md' for
implementation evidence, README files for workflows, and skills for recurring
technical reasoning. Do not document hypotheses as rules or duplicate one
decision across multiple sources without a clear purpose.

## Skills

Select the minimum skill whose 'name' and 'description' match the task. Read it
completely before applying it. Combine skills only across real boundaries.
Skills must be specific, non-ambiguous, independent, and free of references to
other skills. Do not create a skill for a one-off task.

## Branches and recovery

Permanent branches are:

- 'main': production-ready history;
- 'develop': integration history for approved, unreleased work.

Create temporary branches from 'develop':

~~~text
feature/<scope>-<slug>
fix/<scope>-<slug>
refactor/<scope>-<slug>
test/<scope>-<slug>
docs/<scope>-<slug>
chore/<scope>-<slug>
~~~

Create 'hotfix/<scope>-<slug>' from 'main'. Merge the hotfix into 'main'
first, then incorporate it into 'develop'. Never commit directly to protected
branches, force-push shared branches, rewrite shared history, or use
destructive recovery commands. Use 'git revert' through a corrective branch.

## Commits and Pull Requests

Use Conventional Commits:

~~~text
type(scope): short description
~~~

Keep commits atomic and separate unrelated changes. Large work may use
checkpoint commits. The normal flow is:

~~~text
work branch → Pull Request to develop → Pull Request from develop to main
~~~

Pull Requests remain required even when the owner is the only maintainer:
they provide the diff, CI gate, decision record, and reversible unit. An agent
may prepare a PR but must not merge it without explicit authorization.

## Versioning and releases

The root 'package.json' is the single version source for the coordinated
monorepo. The current development version is '0.0.1'. Use tags only for
coherent states published from 'main':

~~~text
v0.0.x  technical snapshots
v0.1.0  first coherent minimally functional release
v0.1.x  compatible fixes before 1.0
v0.2.0  significant evolution
v1.0.0  stable product and public contracts
~~~

Only the owner or an authorized release maintainer may create or publish tags.
An agent may prepare the release checklist but must not create, push, move,
overwrite, or delete a release tag without explicit authorization. Protect
published 'v*' tags in the remote repository.

## Commands and validation

Run commands from the repository root. The local equivalent of CI is:

~~~bash
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm build
pnpm openapi:check
~~~

Use narrower validation when appropriate:

~~~bash
pnpm dev:setup
pnpm dev
pnpm start
pnpm test:unit
pnpm test:integration:auth
~~~

Integration authentication tests require the test Docker services and test
environment. Never claim a command passed unless it completed successfully.

## Documentation and handoff

Update README or documentation when changing architecture, scripts,
dependencies, infrastructure, tests, deployment, branches, releases, or a
reusable pattern. The final handoff must state what changed, where it changed,
what evidence and commands passed, what was not run, remaining uncertainty,
and which documentation or skills were updated.
